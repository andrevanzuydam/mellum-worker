## Demo and product interpretation

**Recommendation:** Prefer project facts over a rehearsed sequence of tool
calls. Confidence is high that run/test commands belong in project notes;
the effect of a positive retrieval instruction is still unmeasured here.
Keep the demo's prompt short enough to show natural task delegation, and
report retries or extra constraints when they were needed.

Bare Pi loads normal context files. Pi Mode forwards only the bounded
`## Mellum` bullets and its fallback; the Pi Worker receives its brief and
worker prompt. OpenCode's Worker has its own host integration. A bullet
working in bare Pi does not establish that any of these other paths receives
it or benefits from it. For each shipping candidate, name the mechanism:
shared prompt/template, setup guidance, project-fact forwarding, run-record
analysis, or a host-specific integration. Validate the applicable paths;
label OpenCode behavior unmeasured until exercised on that host.

Next: when Paul requests runs, establish the baseline and compare one
instruction or prompt refinement at a time. Translate repeatable failures
into an eval with behavior checks, not an assertion that the model must
choose a particular command. Preserve environment and process-cleanup
failures as runner candidates as well as model observations.

## What would falsify this

The approved general AGENTS.md and neutral prompt were subsequently tried
with n=2, without red/green guidance: one empty-final failure, one independently
verified success. Both were judged by a separate DeepSeek model; see the
[experiment record](2026-10-11-natural-agents-n2.md). The project candidate
is now installed in ac-demo; the shared worker recipe remains unchanged.

Follow-up analysis and candidate remedies are in
[Natural project instructions](2026-10-11-natural-project-instructions.md),
including the normal context-loading explanation, seven-probe reread count,
a proposed general AGENTS.md and a separate test-first policy comparison.

- Controlled repetitions show the proposed facts do not reduce scans,
  requests, or context growth, or reduce correctness on other tasks.
- A refinement only succeeds with solution-specific instructions or hidden
  grading knowledge; it is unsuitable as a general demo/product lesson.
- A host does not receive the relevant facts or behaves differently under
  its shipped prompt/tools; the transfer claim fails for that host.

## Risks

- One successful two-file task cannot establish general reliability.
- Changed starting files, context, cache warmth, or server settings can
  confound comparisons; ~20 s per run is an observation, not a budget.
- Repeated demo tuning can overfit a single task. Retain baseline evidence
  and use existing ladder tasks before promoting measured behavior changes.
- Local session paths can disappear. Preserve provenance before claiming
  durable or publicly reproducible results.
